# 描画の統合テストと GPU 時間の測定

## はじめに

集中線のソースの出力を画素で検査する統合テストを作り、Windows の D3D11 と、Windows・Ubuntu・macOS の OpenGL で実行しました。あわせて、1920×1080 での 1 フレームあたりの GPU 時間を測りました。目標は、依頼者の RTX 3060 Ti で 1 ms 未満です。作業は PR #2 で main にマージしました。

## 検証環境

| 項目 | 値 |
| --- | --- |
| 手元の GPU | NVIDIA GeForce RTX 3060 Ti、ドライバー 32.0.16.1088 |
| 手元の OS | Windows 11 Home |
| ビルドに使う OBS | 31.1.1 |
| CI の Windows | `windows-2022`。GPU が無く、D3D11 は Microsoft Basic Render Driver で動く |
| CI の Ubuntu | `ubuntu-24.04`。Mesa の OpenGL を xvfb で使う |
| CI の macOS | `macos-15`。OpenGL |

## 検証方法

統合テストは `tests/integration-test.cpp` です。テスト用に libobs をフロントエンドなしで起動し、プラグインを読み込んでソースを作り、出力を読み出して検査します。シナリオは次の 7 つです。

| シナリオ | 検査の内容 |
| --- | --- |
| empty-center | 既定の設定で線が描かれ、中心の空白の楕円の内側がすべて透明である |
| empty-center-shape | 中心を動かし、縦横比 4 の空白でも内側がすべて透明である |
| color | 不透明の赤の線の画素が赤で、最も濃い画素の不透明度が 255 である |
| opacity | 不透明度 50% の赤の線で、最も濃い画素の不透明度が 128 である |
| settings-update | 同じソースの設定を変えると、線の本数と空白の大きさに従って描かれる画素の数が変わる |
| animation | 描き替えの頻度が 0 なら 500 ms 後も出力が同じで、12 なら変わる |
| custom-size | 幅と高さを指定すると、その大きさで出力され、空白の内側が透明である |

手元では CTest で D3D11 と OpenGL の両方に登録し、CI では `.github/workflows/render-test.yaml` で 3 つの OS で実行します。環境変数 `BURST_TEST_OUTPUT_DIR` を指定すると、比較に使った画像を BMP で書き出します。CI はこの画像を成果物に含めます。

GPU 時間はベンチマーク `tests/benchmark.cpp` で測りました。1920×1080 の描画先にソースを描く処理を 60 フレーム続け、その前後を GPU のタイムスタンプで挟みます。これを 5 回繰り返した中央値を 1 フレームあたりの時間とします。描画先を消去するだけの時間を基準として、あわせて出します。

## 検証結果

### 統合テスト

手元の ctest では、D3D11 と OpenGL の 14 件すべてが合格しました。PR #2 の最後の CI でも、Windows の D3D11・Ubuntu・macOS の 7 件ずつがすべて合格しました。

既定の設定で描かれる画素の数は、320×180 の出力で OS ごとに次のとおりでした。

| 環境 | 描かれる画素の数 |
| --- | --- |
| 手元の D3D11 | 8,016 |
| 手元の OpenGL | 8,019 |
| CI の Ubuntu | 7,899 |
| CI の macOS | 7,716 |

### GPU 時間

手元の RTX 3060 Ti での結果は次のとおりです。

| 描画方式 | 線の本数 | 1 フレームの時間 | 消去だけの時間 |
| --- | --- | --- | --- |
| D3D11 | 120 | 0.044 ms | 0.000 ms |
| D3D11 | 400 | 0.040 ms | 0.000 ms |
| OpenGL | 120 | 0.047 ms | 0.006 ms |
| OpenGL | 400 | 0.047 ms | 0.006 ms |

CI の Ubuntu では、線 120 本で 0.045 ms でした。CI の Windows では、ソフトウェアの描画のため 15.4 ms でした。CI の macOS では、タイムスタンプが取れず測れませんでした。

### 途中で失敗した検査

settings-update は、最初の実行で D3D11 と OpenGL の両方で失敗しました。設定を 3 回変えても、描かれる画素の数が 8,016 のまま変わりませんでした。libobs の `obs-source.c` の 967 行と 1265 行では、映像のソースの `obs_source_update` は数を数えるだけで、反映は次のフレームの `video_tick` で行われます。テストが設定の直後に描いていたため、設定を変えたあとは OBS のフレームが 2 つ進むのを待ってから描くよう直しました。

animation は、CI の macOS だけで失敗しました。描き替えの頻度が 0 でも、500 ms の前後で 57,600 画素のうち 138 画素が違いました。作成直後の 1 枚目、続けて描いた 2 枚目、500 ms 後の 3 枚目を比べると、1 枚目と 2 枚目で 273 画素が違い、2 枚目と 3 枚目は一致しました。依頼者が差分の画像を目視し、1 枚目の上端の数行だけに前の内容が残っていることを確かめました。テストでは、最初の 1 回の描画を捨ててから比べるよう直しました。

ベンチマークは、OpenGL では基準の測定で失敗しました。OpenGL の libobs の `gs_timer_range_create` は常に NULL を返します。範囲が無いときは範囲の開始と終了を省くよう直しました。

## 考察

GPU 時間は、目標の 1 ms 未満を大きく下回っています。線の本数を 120 から 400 に増やしても時間がほぼ変わらないのは、1 画素あたりの計算が線の本数によらないためだと考えています。消去だけの時間が D3D11 で 0.000 ms と出たのは、表示の桁の 0.001 ms より短いためだと考えています。

既定の設定で描かれる画素の数が OS ごとに違うのは、乱数に使う `sin` などの浮動小数の計算の結果が、描画方式ごとにわずかに違うためだと推測します。どの環境でも中心の空白などの検査に合格しているため、直す必要は無いと考えています。

macOS の animation の失敗は、プロセスで最初に読み出した画像の上端だけが古いことから、テストの読み出しが GPU の書き込みに追いついていなかったためだと考えています。実際の OBS ではソースを毎フレーム描き直すため、配信の画面には影響しないと考えています。
